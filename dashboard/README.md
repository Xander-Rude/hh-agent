# HH Agent Observatory — безопасный локальный MVP

Отдельный FastAPI backend и dark/neon frontend с разделами LIVE, ANALYTICS и RESUME.
LIVE построен вокруг светящейся схемы COLLECT → FILTER → SCORE → REVIEW → APPLY:
источники слева, модули справа, четыре счётчика и лента событий снизу. Клик по этапу
выбирает его лог. Подробный runtime свёрнут, графики находятся в ANALYTICS.
Стилистика адаптирована из [rudenko.one](https://rudenko.one/): Manrope, фон `#0a0a0a`,
белые карточки, синий `#0088cc` и фиолетовый `#6c3bff`. Тема вынесена в
`static/theme.css`. Латиница и кириллица Manrope включены локально под SIL OFL
(`static/fonts/OFL.txt`), из [Google Fonts](https://github.com/google/fonts/tree/main/ofl/manrope).
Интерфейс не делает запросов к Google Fonts или другим внешним сервисам.
Модуль только читает существующие источники. Никаких изменений worker/pipeline/apply/
resume_raise, планировщика Windows, фоновых задач или обязательных `emit_event`.

## Запуск в PowerShell (Python 3.12+)

Работайте в **отдельном checkout ветки dashboard**. `C:\hh-agent` может продолжать
работать со своим окружением и расписанием. Например, после получения PR:

```powershell
git clone --branch feat/isolated-readonly-dashboard https://github.com/Xander-Rude/hh-agent.git C:\hh-agent-dashboard
cd C:\hh-agent-dashboard
py -3.12 -m venv dashboard\.venv
.\dashboard\.venv\Scripts\python.exe -m pip install -r dashboard\requirements.txt
.\dashboard\.venv\Scripts\python.exe -m dashboard --source-root C:\hh-agent
```

Откройте **http://127.0.0.1:8765**. Сервер работает в текущем окне до **Ctrl+C**.
Если порт занят, добавьте `--port 8766`. Модуль запускается только на `127.0.0.1`;
не публикуйте его через прокси: логи могут содержать личные данные.

`--source-root` — корень существующего рабочего агента; он не меняется dashboard.
Без аргумента читаются `data/` и `logs/` в checkout самого dashboard.
Если источников нет, панель запускается и показывает **N/A**, не создавая БД или runtime.
Окружение `dashboard/.venv` отдельное; зависимости рабочего агента не обновляются.
Для удаления достаточно остановить панель и удалить отдельный checkout.

## Что видно и откуда берётся

| Показатель | Источник и смысл |
| --- | --- |
| Pipeline / apply / Telegram / resume raise | `data/runtime/{pipeline,apply,telegram,resume_raise}.json`: последнее сохранённое `status`, `stage`, `updated_at`, `pid`, ошибка |
| Heartbeat процесса | **N/A**: периодический heartbeat в этих файлах не сохраняется. Показан отдельный возраст записи состояния |
| Последние события | Исходные последние 80 строк выбранного файла из фиксированного списка `logs/`; без выдуманных временных меток |
| Apply today | `applications`: текущий `status='applied'` и `applied_at` внутри московского дня; все источники и резюме |
| Накопленные counters | Число сохранённых строк `vacancies`, `evaluations`, `applications`; распределение текущих `applications.status` |
| Источники | Число строк по `vacancies.source`, без предположений об online/offline |
| Графики | Отклики по московским дням за 14 дней, распределение `evaluations.score` от 0 до 100 |
| Single-resume experiment | Заданные пользователем ID `ed318343ff109278200039ed1f674d474e5336`, title «Руководитель IT-программ и портфеля проектов», start `2026-09-12` |
| Отклики эксперимента | `status='applied'`, точное совпадение `selected_resume_id`, `applied_at` с 12.09.2026 00:00 МСК до времени чтения БД |
| Просмотры / приглашения / накопленные подъёмы | **N/A**: подтверждённых счётчиков в текущей БД нет |

`app/db.py` хранит даты БД как UTC без timezone; границы московского дня
переводятся в UTC (Москва — UTC+03:00). Runtime использует ISO timestamps с offset.
Параметры эксперимента — метаданные панели, **не подтверждение конфигурации**
`data/resumes.yaml`. Dashboard не импортирует и не запускает `configure_single_resume.py`.

`updated_at` меняется при записи состояния, не периодически. Даже давняя запись
`running` не доказывает зависание; PID не проверяется через список процессов.
`ok` — последнее успешное завершение supervisor, а не подтверждение отправки отклика.
Схема — карта обработки, а её счётчики относятся к сохранённым данным, не к одной
сквозной когорте вакансий (оценок может быть больше, чем вакансий). Движение на связи
появляется только при записи `running` нужного этапа младше 120 секунд. Это подсветка
недавней записи, не новый источник heartbeat. Для `process` вместе подсвечиваются
FILTER/SCORE: runtime не различает внутренние шаги обработчика. Статичная схема не
перерисовывается постоянно; скрытая вкладка и reduced motion останавливают анимацию.
Старые `finished_at`/`exit_code` скрываются для `starting`/`running`, потому что runtime
сливает новые поля со старым JSON. Windows Task Scheduler не опрашивается.

Ноль показывается только при успешном подсчёте и отсутствии подходящих строк.
Отсутствующая таблица/колонка, повреждённый файл или занятая БД дают N/A и пояснение.
Удалённые записи и исторические переходы статусов не восстанавливаются из воздуха.

## Изоляция и нагрузка

- Код и зависимости только в `dashboard/`; нет импорта `app.db` (он запускает миграции
  при импорте), бизнес-модулей, `init_db`, планировщиков или запуска worker.
- SQLite открывается напрямую через `mode=ro` и `PRAGMA query_only=ON`.
  Никаких миграций, индексов, `journal_mode`, checkpoint или изменений business state.
  `immutable` и `nolock` не используются: рабочая БД может меняться, включая WAL.
  Действуют обычные краткие read-locks SQLite; при WAL используются его существующие
  механизмы shared memory. Поддерживается только локальный диск, не сетевой share.
- Таймаут ожидания SQLite lock — 50 мс, progress handler прерывает SQL после
  бюджета 200 мс. Соединение сразу закрывается. Это не жёсткий таймаут дискового I/O.
  БД кэшируется на 30 секунд на один сервер; вкладки не умножают частоту запросов.
  Все счётчики одного ответа читаются в короткой read transaction, чтобы параллельные
  записи агента не приводили к несогласованным итогам.
- Runtime JSON ограничен 64 KiB на файл. Log tail читает максимум последние 64 KiB
  и до 200 строк через API. При обрезке первая неполная строка отбрасывается.
- Автообновление браузера каждые 5 секунд, без наложения запросов; скрытая вкладка
  приостанавливает опрос. Связь с панелью не считается сигналом жизни агента.
- Только GET endpoints, фиксированный список логов, запрет выхода symlink за root,
  локальные Host, без CORS и внешних CDN. Логи вставляются как текст, не HTML.
  При обрыве связи последний снимок помечается устаревшим.

API: `GET /api/snapshot`, `GET /api/logs/{name}?lines=80`. Пустые значения — JSON `null`,
интерфейс показывает их как `N/A`. `database.sampled_at` — время чтения БД, а
`sampled_at` верхнего уровня — время снимка runtime; это разные показатели свежести.

## Проверка отдельно от агента

```powershell
.\dashboard\.venv\Scripts\python.exe -m pip install -r dashboard\requirements-dev.txt
.\dashboard\.venv\Scripts\python.exe -m unittest discover -s dashboard\tests -v
```

Тесты работают только во временных папках: read-only и неизменность файлов,
отсутствующие/старые/повреждённые источники, занятая SQLite и WAL с параллельным writer,
границы московского дня, привязка к резюме, runtime без ложного heartbeat,
UTF-8 log tail/ротация, ограничение API, кэш и отдача frontend.

Решение использует стандартные механизмы [SQLite URI read-only](https://www.sqlite.org/uri.html)
и [FastAPI StaticFiles](https://fastapi.tiangolo.com/tutorial/static-files/).
